# ingest_worker

Микросервис обработки и индексации документов для RAG-системы. Он забирает документы со статусом `pending` из PostgreSQL, загружает исходный файл, извлекает текст, автоматически выбирает стратегию чанкинга, генерирует embeddings и сохраняет чанки и векторы в PostgreSQL/pgvector.

**Важно:** сервис является background worker, а не HTTP API. Отдельных REST endpoints в текущей реализации нет; интеграция с другими сервисами происходит через PostgreSQL.

## Быстрый запуск

### Локально

1. Установить зависимости:

```bash
pip install -r requirements.txt
```

2. Создать `.env` на основе `.env.example` и указать минимум `DATABASE_URL`.
3. Запустить worker:

```bash
python app/main.py
```

Worker ждёт уведомления о новых документах (`LISTEN ingest_jobs`) и забирает их сразу; см.
раздел «Очередь и повторы». Перед первым запуском на существующей базе примените
`main/infra/db/migrations/006_ingest_queue.sql`.

### Docker

Сервис описан в общем `main/docker-compose.yml` и собирается вместе со стеком:

```bash
cd main && docker compose up -d --build ingest-worker
```

Порт наружу не публикуется — это background worker без HTTP-сервера. Healthcheck в compose
проверяет свежесть heartbeat-файла `/tmp/ingest-worker.heartbeat`: воркер обновляет его каждые
`HEARTBEAT_INTERVAL_SEC` секунд, начиная с момента, когда пройдены стартовые проверки
(доступность `embedding-svc` и размерность колонки в БД). Файл старше 60 с — воркер не
стартовал или завис.

> Раньше `Dockerfile` в репозитории был **пустым файлом**, из-за чего сборка контейнера
> падала и воркер вообще нельзя было поднять. Сейчас он восстановлен: ставит зависимости и
> запускает `python app/main.py`.

---

Микросервис обработки документов для RAG-системы.
Читает задачи из PostgreSQL, парсит файлы, нарезает на чанки, сохраняет векторные эмбеддинги.

## Архитектура

```
PostgreSQL (library.documents)
        │  pending
        ▼
  IngestWorker (main.py)
        │
        ├── parse_pdf   → SmartChunker (M5 или M4)
        ├── parse_docx  → SmartChunker (M5 или M2)
        └── parse_txt   → SmartChunker (M2)
        │
        ▼
  embedding-svc POST /embed   ← единственный источник векторов в системе
        │
        ▼
  library.chunks + library.chunk_embeddings
```

Своей модели эмбеддингов у воркера нет: и он, и `graph-rag-svc` считают векторы через
`embedding-svc`, поэтому чанки и поисковые запросы гарантированно лежат в одном векторном
пространстве. Размерность (`EMBEDDING_DIM`) сверяется при запуске и с моделью, и с колонкой
в БД — при расхождении воркер не стартует.

## Очередь и повторы

Схема (колонки и триггеры) — в `main/infra/db/init/init.sql`, для существующих баз —
`main/infra/db/migrations/006_ingest_queue.sql`.

**Доставка задач — `LISTEN/NOTIFY`.** Триггер `trg_documents_ingest_notify` на
`library.documents` шлёт `pg_notify('ingest_jobs', id)`, когда документ вставлен или
переведён в `pending`. Воркер держит отдельное соединение asyncpg с `LISTEN` и просыпается
сразу. Выбран именно такой способ, а не брокер сообщений: документы создают несколько
сервисов (`library-svc`, `db-svc`, `crawler-svc`, ручные правки через админку), и уведомление
от самой БД работает при любом способе записи, не требуя менять ни один из них. Опрос
остаётся страховкой: раз в `INGEST_POLL_FALLBACK_SEC` (60 с), а при потере соединения `LISTEN`
— раз в `INGEST_POLL_DEGRADED_SEC` (5 с) с переподключением на каждом круге. Обрыв
соединения будит воркер сразу. NOTIFY доставляется при COMMIT, поэтому незакоммиченную
строку воркер не увидит.

**Какой документ берётся в работу** (`SELECT ... FOR UPDATE SKIP LOCKED`):

- `pending`, у которого `ingest_next_attempt_at` пуст или наступил;
- `processing`, у которого `ingest_started_at` старше `INGEST_PROCESSING_TIMEOUT_SEC` (или пуст
  — застрявшие до миграции). Раньше документ, на котором воркер упал или был перезапущен,
  навсегда оставался в `processing`: статус коммитится до обработки.

**Повторы.** Каждая попытка увеличивает `ingest_attempts`. При ошибке:

| Ошибка | Результат |
| :-- | :-- |
| `PermanentIngestError` (`app/errors.py`): файл больше `MAX_FILE_SIZE_MB`, файл не разбирается парсером | сразу `failed` — повтор не поможет |
| любая другая (недоступен `embedding-svc`, MinIO, БД) и попытки не кончились | снова `pending`, `ingest_next_attempt_at = now() + INGEST_RETRY_BASE_SEC · 2^(попытка−1)`, не больше `INGEST_RETRY_MAX_SEC` |
| любая другая на попытке `INGEST_MAX_ATTEMPTS` | `failed` |

`ingest_error` хранит текст последней ошибки с номером попытки. Документ, на котором воркер
падает целиком (например, по памяти) и не успевает записать ошибку, возвращается по таймауту
`processing`; когда попытки у него кончаются, он получает `failed` без новой обработки —
иначе такой документ валил бы воркер бесконечно.

Успешная индексация обнуляет `ingest_attempts`. Триггер `trg_documents_ingest_reset`
обнуляет счётчик и задержку, когда документ возвращают в `pending` из `indexed`/`failed`
(новая версия или ручной reindex), — у него снова полный запас попыток.

## Стратегия чанкинга (SmartChunker)

Выбор метода производится автоматически на основе типа и структуры документа.
Итоги внутреннего бенчмарка (метрика: **cohesion = intra_sim − inter_sim**):

| Формат | Условие                      | Метод                   | Cohesion     |
| ------------ | ----------------------------------- | ---------------------------- | ------------ |
| PDF          | есть оглавление (TOC) | **M5 Structure-aware** | лучший |
| PDF          | нет оглавления         | **M4 Recursive**       | +0.007       |
| DOCX         | есть Heading 1/2/3              | **M5 Structure-aware** | +0.035       |
| DOCX         | нет заголовков         | **M2 Sentence**        | —           |
| TXT          | всегда                        | **M2 Sentence**        | +0.047       |

> HTML-страницы конвертируются в TXT во внешнем сервисе и поступают как `.txt`.

### Методы чанкинга

- **M2 Sentence** — разбивка по предложениям, группировка до `CHUNK_SIZE` токенов. Лучший cohesion на TXT.
- **M4 Recursive** — рекурсивная нарезка по иерархии `\n\n → \n → ". " → " "` с перекрытием. Лучший для PDF без структуры.
- **M5 Structure-aware** — нарезка по секциям из TOC (PDF) или Heading-стилей (DOCX). Секции > `CHUNK_SIZE` дробятся через M4.

## Формат данных в БД

`library.chunks`:

- `text` — текст чанка с header injection (`Документ: ... / Категория: ... / ---`)
- `section_path` — заголовок раздела (из TOC или Heading)
- `start_offset` / `end_offset` — байтовые позиции в исходном тексте
- `token_count` — оценочное число токенов
- `metadata_json` — полный набор метаданных: `doc_type`, `chunk_method`, `chunk_index`, и др.

`library.chunk_embeddings`:

- `embedding` — вектор размерности `EMBEDDING_DIM` (1024 для `mxbai-embed-large-v1`), как есть,
  без дополнения нулями и без обрезки
- `embedding_model` — имя модели, которое вернул `embedding-svc` (авторитетный источник)

## Технические проблемы и ограничения

Ниже перечислены проблемы, которые следует учитывать перед production-эксплуатацией.

### Высокий приоритет

1. ~~**Нет healthcheck/readiness endpoint.**~~ **Исправлено.** Worker нельзя было проверить
   как живой/готовый сервис. HTTP-сервер ради этого не заводили: воркер обновляет
   heartbeat-файл, а healthcheck в compose проверяет его свежесть (см. «Docker»). Файл
   появляется только после стартовых проверок, а разбор файлов вынесен в поток
   (`asyncio.to_thread`), чтобы большой PDF не останавливал event loop и heartbeat.
2. ~~**Нет retry/backoff для отдельных документов.**~~ **Исправлено.** Любая ошибка сразу
   давала `failed`, в том числе кратковременная недоступность `embedding-svc` или MinIO; а
   документ, на котором воркер упал, навсегда оставался в `processing`. Теперь повторы с
   экспоненциальной паузой, отдельный класс неповторяемых ошибок и возврат брошенных
   `processing` — см. «Очередь и повторы».
3. ~~**Опасное поведение при ошибке загрузки embedding-модели.**~~ **Решено.**
   Раньше при неудачной загрузке `SentenceTransformer` код создавал нулевые векторы вместо остановки обработки, и документ мог получить статус `indexed` без пригодного эмбеддинга. Собственной модели у воркера больше нет: неудачный вызов `embedding-svc` честно роняет обработку документа в `failed`.
4. ~~**Несовпадение размерности эмбеддинга с реальной колонкой БД.**~~ **Решено.**
   Раньше `ChunkEmbedding.embedding` был объявлен как `Vector(1536)`, а `_embed()` дополнял нулями и обрезал векторы до 1536 измерений, тогда как фактическая колонка `library.chunk_embeddings.embedding` — `VECTOR(1024)`. pgvector отклонял такую вставку, а поскольку чанки и эмбеддинги пишутся одной транзакцией, откатывались **и уже созданные `library.chunks`** — документ целиком помечался `ingest_status='failed'`. Кроме того, воркер не обращался к `embedding-svc`, а грузил собственную модель, так что в системе было два независимых источника эмбеддингов, согласованных только совпадением значений в двух разных `.env`.

   **Что сделано** (полный разбор, включая разбор варианта «объявить размерность с запасом и дополнять нулями», — в README `graph-rag-svc`, §13.1): эмбеддинги считает только `embedding-svc`; дополнение и обрезка удалены; имя модели берётся из ответа сервиса; размерность объявляется один раз (`EMBEDDING_DIM` в корневом `.env`) и на старте сверяется и с моделью, и с фактическим типом колонки в БД — при расхождении воркер не запускается.

   **Проверить на существующей базе:** документы, упавшие до этой правки, остались в статусе `failed` и требуют переиндексации — `SELECT ingest_status, count(*) FROM library.documents GROUP BY ingest_status;`. Также нужно удалить строки с нулевыми векторами, если они успели записаться: они находятся условием `embedding <-> embedding = 0`.
5. ~~**Нет ограничения максимального размера файла.**~~ **Исправлено.** Файл целиком
   загружался в память, и один огромный файл мог уронить воркер по OOM. Теперь
   `MAX_FILE_SIZE_MB` (50): для S3 и локальных файлов размер проверяется до чтения, для HTTP
   — по `Content-Length` и затем по мере чтения потока. Превышение — сразу `failed`.

### Средний приоритет

6. **HTTP-загрузка имеет фиксированный timeout 15 секунд.**
   Для больших документов или медленного хранилища этого может быть недостаточно.
7. ~~**Polling вместо очереди сообщений.**~~ **Исправлено.** Опрос раз в 5 с давал задержку
   до 5 с на каждый документ и постоянные запросы в простое. Теперь `LISTEN/NOTIFY` по
   триггеру в БД, опрос — только страховка раз в 60 с (см. «Очередь и повторы»).
8. **HTML зависит от внешнего сервиса.**
   Worker сам HTML не парсит: HTML должен быть заранее преобразован во внешний TXT.
9. **Ограниченная обработка содержимого документов.**
   Pipeline ориентирован на текст. Отдельного извлечения изображений, таблиц и другого мультимедийного содержимого нет.
10. **Нет отдельного механизма ручного запуска/reindex.**
   Для повторной обработки нужно управлять статусом документа через БД или реализовать дополнительный orchestration-механизм.

### Рекомендации

Перед production рекомендуется как минимум:

- добавить метрики (health, retry, лимит размера и доставка задач уже сделаны);
- добавить лимит времени обработки одного файла (сейчас от зависания страхует только
  `INGEST_PROCESSING_TIMEOUT_SEC`, и то лишь после перезапуска воркера);
- предусмотреть безопасный механизм reindex (сейчас — перевод документа в `pending`, триггер
  сам вернёт ему полный запас попыток).

## Подключение к PostgreSQL по сертификату

Если заданы `POSTGRES_SSLCERT`, `POSTGRES_SSLKEY` и `POSTGRES_SSLROOTCERT`, сервис входит в БД
по клиентскому сертификату (CN равен имени роли) вместо пароля и проверяет сервер: цепочку до
корня и имя хоста. Это делает `app/pg_tls.py`: он создаёт движок со своим `async_creator` и
собирает контекст TLS заново для каждого нового соединения, чтобы обновлённый сертификат
(он живёт сутки) подхватывался без перезапуска. Без этих переменных сервис работает как раньше,
по паролю из URL. Модуль одинаков во всех сервисах и лежит в каждом репозитории отдельной
копией, менять его нужно во всех сразу. Включение и проверка — `main/infra/db/README.md`.

## Вызовы других сервисов по mTLS

Так ingest-worker вызывает embedding-svc (`/embed`, `/ping`).

Если заданы `SERVICE_MTLS_CERT`, `SERVICE_MTLS_KEY` и `SERVICE_MTLS_CA`, сервис предъявляет свой
сертификат внутреннего CA (CN равен имени сервиса) и проверяет сервер. Контекст TLS собирается в
`app/mtls.py` заново при создании каждого HTTP-клиента, поэтому суточный сертификат,
обновлённый рядом лежащим контейнером, подхватывается без перезапуска. Без этих переменных
сервис работает как раньше, по открытому HTTP с токеном `X-Service-Token`. Получатели
(graph-rag-svc, embedding-svc) принимают вызовы только через прокси с проверкой сертификата и
политикой «кто что может» (`main/infra/mtls`). Модуль одинаков в chat-svc, db-svc,
graph-rag-svc и ingest-worker, менять его нужно во всех сразу. Включение и проверка —
`main/infra/pki/README.md`, раздел «mTLS между сервисами».
